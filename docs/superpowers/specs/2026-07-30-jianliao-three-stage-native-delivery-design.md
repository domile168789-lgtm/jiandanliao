# 柬聊三段式原生双端交付设计

## 背景

当前仓库已经完成了以下基础能力：

- `apps/api`：认证、会话、消息、文件上传、群聊生命周期、风控与举报闭环
- `apps/ws`：基础实时服务与健康检查
- `apps/web`：H5 四 Tab 路由、强登录守卫、基础消息页与占位页

用户本轮明确要求：

- 最终目标不是只收 H5，而是 `H5 + Android + iOS`
- Android 与 iOS 采用 **各自原生双写**
- 需要把剩余开发“一次性全部做完”，但前提是交付必须稳定、可构建、可联调、可回归

基于当前仓库现状，Android / iOS 尚无成熟客户端工程骨架，因此不适合把所有剩余工作当作一个单一实现任务直接并行开工。必须先把后端协议与 H5 联调基准端收口，再推进 Android，最后推进 iOS。

## 设计结论

本项目后续开发拆分为 3 个连续子项目：

1. `协议与后端收口 + H5 联调基准端`
2. `Android 原生端`
3. `iOS 原生端`

只有前一阶段达到约定完成标准，后一阶段才开始实施。

## 为什么必须三段式

### 不采用“一次三端齐推”

原因：

- 当前可直接续写的客户端只有 `apps/web`
- Android / iOS 若现在同步开工，会在接口字段、已读未读、文件上传、WS 事件、消息体结构上反复返工
- 一次三端齐推会把问题放大成三份，最终更慢，而不是更快

### 不采用“H5 做完即视为全部完成”

原因：

- 用户已明确要求 Android / iOS 原生双写
- H5 只能作为协议验证端，不能替代原生端交付

### 采用“三段式串行 + 协议优先”

收益：

- 每一阶段都有明确验收口径
- Android 与 iOS 都基于已经稳定的协议实现
- H5 可以作为联调对照组，帮助快速定位是协议问题还是原生端实现问题

## 子项目 1：协议与后端收口 + H5 联调基准端

### 目标

把 `apps/api + apps/ws + apps/web` 收口到“可作为 Android / iOS 联调标准”的状态。

### 范围

#### 后端

- 补齐并稳定以下接口/行为：
  - 会话分页与详情
  - 消息分页
  - 会话已读与未读清零
  - 联系人列表
  - 我的信息
  - 登出
  - WebSocket 事件一致性
- 统一协议字段命名与消息体结构
- 确保图片、语音上传返回结构可被三端复用
- 确保群聊、系统消息、风控拦截都参与统一协议

#### H5

- 真正接入登录态持久化
- 接入会话列表 API
- 接入聊天页消息拉取与文本发送
- 接入图片上传发送
- 接入语音上传发送
- 展示系统消息会话
- 接入联系人与“我的”页面真实数据
- 接入已读/未读与 WebSocket 更新

### 完成标准

- `apps/api` 可构建、测试通过
- `apps/ws` 可启动并能向 H5 推送已定义事件
- `apps/web` 可构建、基础测试通过
- H5 端到端可演示以下闭环：
  - 登录
  - 会话列表
  - 进入聊天页
  - 文本发送
  - 图片发送
  - 语音发送
  - 系统消息展示
  - 群聊进入与消息展示
  - 已读/未读变化

### 本阶段产出

- 稳定协议基线
- H5 联调基准端
- Android / iOS 开发所需的对照实现

## 子项目 2：Android 原生端

### 目标

基于子项目 1 已稳定的协议，实现 Android 原生端完整 IM 主链路。

### 范围

- 登录与登录态持久化
- 四 Tab：消息 / 通讯录 / 发现 / 我的
- 会话列表
- 聊天页
- 文本消息发送
- 图片上传与图片消息发送
- 语音录制、上传、发送、播放
- 系统消息会话
- 群聊列表与群聊进入
- 已读 / 未读同步
- WebSocket 实时同步

### Android 特有要求

- 使用 Android 推荐存储方案保存 token
- 语音录制与播放使用 Android 原生能力
- 图片选择、录音权限、前后台切换恢复等按 Android 规范处理

### 完成标准

- 工程可构建
- 安装后可登录
- 文本 / 图片 / 语音三类消息都可发送与接收
- 可接收系统消息
- 可展示会话未读变化
- 基础测试或最小回归清单可执行

## 子项目 3：iOS 原生端

### 目标

在与 Android 同协议、同能力口径下，实现 iOS 原生端完整 IM 主链路。

### 范围

- 登录与登录态持久化
- 四 Tab：消息 / 通讯录 / 发现 / 我的
- 会话列表
- 聊天页
- 文本消息发送
- 图片上传与图片消息发送
- 语音录制、上传、发送、播放
- 系统消息会话
- 群聊列表与群聊进入
- 已读 / 未读同步
- WebSocket 实时同步

### iOS 特有要求

- 使用 iOS 安全存储保存 token
- 使用 iOS 原生音频能力完成录音与播放
- 处理麦克风、相册权限与前后台恢复

### 完成标准

- 工程可构建
- 安装后可登录
- 文本 / 图片 / 语音三类消息都可发送与接收
- 可接收系统消息
- 可展示会话未读变化
- 基础测试或最小回归清单可执行

## 统一协议约束

以下内容必须在三端保持一致，不允许“UI 看起来差不多但行为不同”：

- 会话类型：`DM | GROUP | SYSTEM`
- 消息类型：`TEXT | IMAGE | AUDIO | FILE | VIDEO | SYSTEM`
- 摘要规则：
  - `IMAGE -> [图片]`
  - `AUDIO -> [语音]`
  - `VIDEO -> [视频]`
  - `FILE -> [文件]`
  - `SYSTEM -> 标题或 [系统消息]`
- 文件上传响应字段
- WS 事件名与事件结构
- 已读 / 未读语义
- 封禁与风控错误语义：
  - `401 UNAUTHORIZED`
  - `403 FORBIDDEN`
  - `429 TOO_MANY_REQUESTS`

## 实施顺序

### 阶段 1

先做 `api/ws + H5`

原因：

- H5 已有基础
- 成本最低
- 能尽快暴露协议缺口

### 阶段 2

再做 Android 原生端

原因：

- Android 录音、文件选择、权限处理复杂度更高
- 先打掉复杂度更高的一端，有利于后续复用经验到 iOS

### 阶段 3

最后做 iOS 原生端

原因：

- iOS 可以直接对照 Android 与 H5 的既有行为完成一致化

## 明确不做的事情

本设计只定义“三段式交付路径”，不在此阶段承诺以下扩展内容：

- 朋友圈 / 视频号 / 小程序真实业务
- 复杂消息能力：撤回、引用、转发、收藏、置顶、免打扰
- 音频高级处理：降噪、转文字、回声消除
- 多端同时在线的复杂冲突策略
- 推送通知系统的完整生产级接入

## 风险与控制

### 风险 1：协议未冻结就开始原生开发

后果：

- Android / iOS 同时返工

控制：

- 必须先完成子项目 1，协议稳定后再进入原生实现

### 风险 2：H5 与原生行为不一致

后果：

- 同一接口表现不同，排障困难

控制：

- 所有协议字段、错误码、WS 事件都以子项目 1 为唯一基准

### 风险 3：语音链路跨端兼容差

后果：

- 某一端可录但另一端不可播

控制：

- 服务端统一转码
- 三端统一依赖返回的标准音频格式与 MIME

## 验收总原则

每个子项目都必须满足：

- 可构建
- 可运行
- 可登录
- 可拉会话
- 可发文本 / 图片 / 语音
- 可收系统消息
- 可进行基础回归

只有满足这些条件，才视为该阶段完成。

## 最终结论

在用户已明确选择“Android / iOS 各自原生双写”的前提下，本项目必须按以下顺序推进：

1. `协议与后端收口 + H5 联调基准端`
2. `Android 原生端`
3. `iOS 原生端`

这是当前仓库结构下唯一稳定、可交付、且不会导致三端重复返工的路径。
