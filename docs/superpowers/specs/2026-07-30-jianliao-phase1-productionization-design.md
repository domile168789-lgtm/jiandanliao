# 柬聊阶段 1 生产化路线设计

## 背景

柬聊当前已经完成了阶段 1 的多端骨架、共享后端基线、本地联调脚本、后台最小能力、部署基线和 GitHub 文档补齐。从代码和文档准备度看，项目已经具备继续快速收口的基础，但距离“生产运营级 100%”仍有明显差距。

当前最重要的判断是：柬聊不是继续无限扩功能，而是先把阶段 1 从“可联调 MVP”补到“可正式生产运营”。因此后续开发要从以页面和功能为中心，转为以运行环境、稳定性、发布质量、安全和运维为中心。

## 目标

- 把柬聊阶段 1 从当前约 `40%` 的生产度，逐步补到 `100%`
- 先连续推进第一阶段与第二阶段，把整体生产度提升到 `70%`
- 在达到 `70%` 后做一次真实联调复盘，再进入第三阶段和第四阶段
- 避免把阶段 2、阶段 3 的扩功能需求混入当前生产化主线

## 非目标

本设计当前不覆盖以下内容：

- 群聊、好友关系、语音、视频、文件消息等阶段 2 能力扩展
- 本地生活入口、发现页、活动位、运营平台扩展等阶段 3 能力
- 品牌升级、营销增长、商业化结算等长期演进项

## 当前生产度判断

按正式生产运营标准估算，柬聊当前大约处于 `40%` 左右，仍缺约 `60%` 的生产化工作。这个差距主要不在“能不能写出页面”，而在：

- 真实服务器部署闭环
- 后端稳定性与异常处理
- Android / iOS 可发布性
- 后台运营可用性
- 安全与权限
- 运维、监控、发布、回滚和验收体系

## 六条生产化主线

### 1. 运行环境线

这条线负责把项目从“可以在仓库里运行”推进到“可以稳定部署在服务器上”。

要完成的能力包括：

- Rocky 服务器 Docker / Compose 部署跑通
- 域名、Nginx、HTTPS、统一入口打通
- `.env` 驱动的部署方式稳定
- MySQL / Redis / MinIO 的数据持久化
- 备份与恢复链路至少完成一次演练

完成后对整体生产度贡献约 `+10%`，即从 `40%` 提升到 `50%`。

### 2. 后端稳定性线

这条线负责把当前“可联调”的 API / WS 链路补到“可日常使用”。

重点能力包括：

- 登录、消息、上传、回执异常处理
- 消息与回执幂等
- 弱网与重连后的状态补偿
- 关键请求日志、错误日志、审计链路追踪
- 最终业务状态回到 MySQL 校准

完成后整体生产度从 `50%` 提升到 `62%`，贡献 `+12%`。

### 3. 用户端可发布线

这条线负责把 Android / iOS 从联调版推进到可发布版。

重点能力包括：

- Android 构建环境完整跑通
- iOS 真机联调跑通
- 登录、文本、图片、回执、重连体验补齐
- 发送中 / 成功 / 失败的状态反馈
- 真机 / 模拟器地址规范与发布说明

完成后整体生产度从 `62%` 提升到 `72%`，贡献 `+10%`。

### 4. 后台可运营线

这条线负责把 Web / Windows 后台从“最小演示能力”补到“值班与运营可用”。

重点能力包括：

- 用户搜索、筛选、详情
- 封禁原因、确认和结果反馈
- 举报详情与状态流转
- 公告管理而不只是创建
- 审计查询增强

完成后整体生产度从 `72%` 提升到 `80%`，贡献 `+8%`。

### 5. 安全与权限线

这条线负责把阶段 1 中为了快速联调采用的简化方案替换成更接近生产环境的做法。

重点能力包括：

- 管理员正式鉴权替代简化 header 模式
- 密钥、密码、环境变量收口
- 上传访问控制收紧
- 用户侧和管理员侧权限边界明确
- 非必要端口与服务默认配置收敛

完成后整体生产度从 `80%` 提升到 `90%`，贡献 `+10%`。

### 6. 运维与验收线

这条线负责让项目从“单人能部署”推进到“团队可持续运营”。

重点能力包括：

- 日志查看方式统一
- 基础监控与告警
- 发布与回滚流程
- 上线前检查清单
- 日常巡检与故障处理入口
- 产品、运营、技术三类验收表

完成后整体生产度从 `90%` 提升到 `100%`，贡献 `+10%`。

## 四阶段推进方式

为了减少返工，六条主线在执行层面压成四个阶段。

### 第一阶段：把底座跑稳

目标是把整体生产度从 `40%` 提升到 `55%`。

本阶段主要覆盖：

- 运行环境线的大部分内容
- Android 构建环境基础补齐
- 部署文档与一键脚本从“有文档”变成“真实能用”

完成后，柬聊会从“代码已准备”提升到“真实环境底座已建立”。

### 第二阶段：把主链路做稳

目标是把整体生产度从 `55%` 提升到 `70%`。

本阶段主要覆盖：

- 后端稳定性线的核心内容
- iOS / Android 的真实联调主链路
- 上传、回执、重连、补拉等关键链路

完成后，柬聊会具备较稳定的真实联调能力，并具备一次正式复盘的价值。

### 70% 复盘节点

当第一阶段和第二阶段完成后，必须安排一次真实联调复盘。复盘对象包括：

- 服务器部署是否稳定
- Web / Windows 后台的最小操作流是否可连续使用
- iOS / Android 是否能真实互发文本和图片
- 上传与回执链路是否存在明显不稳定点
- 现有日志和排查方式是否足够定位问题

只有通过这次复盘，才进入后续阶段。

### 第三阶段：把前台和后台补到可用

目标是把整体生产度从 `70%` 提升到 `85%`。

本阶段主要覆盖：

- 用户端可发布线的剩余体验项
- 后台可运营线
- 面向真实值班、运营和演示的使用体验优化

完成后，项目将接近“小规模灰度与真实试用”的状态。

### 第四阶段：把工程化收口到生产运营级

目标是把整体生产度从 `85%` 提升到 `100%`。

本阶段主要覆盖：

- 安全与权限线
- 运维与验收线

完成后，项目才算具备正式生产运营级别，而不是仅靠开发人员维持的可运行系统。

## 阶段完成度表

| 阶段 | 主要目标 | 完成后生产度 |
|---|---|---:|
| 当前 | 代码与文档已基本到位 | `40%` |
| 第一阶段 | 底座跑稳 | `55%` |
| 第二阶段 | 主链路做稳 | `70%` |
| 第三阶段 | 前台后台可用 | `85%` |
| 第四阶段 | 工程化与生产化收口 | `100%` |

## 可并行关系

### 可并行

- 运行环境线与 Android 构建环境补齐可以并行
- 后端稳定性线与后台可运营线的一部分可并行
- 用户端可发布线与后台可运营线可并行
- 安全与权限线和运维与验收线中的文档 / 流程部分可并行

### 不建议并行

- 在上传入口和域名未收口前，不建议大规模推进真机上传联调
- 在正式管理员鉴权未定前，不建议大改所有后台交互流
- 在重连、幂等和一致性未稳前，不建议把大量体验调优压到移动端

## 优先级建议

如果目标是尽快接近可运营，最优先顺序是：

1. 运行环境线
2. 后端稳定性线
3. 用户端可发布线
4. 后台可运营线
5. 安全与权限线
6. 运维与验收线

这个顺序能最大限度减少返工，并让每个阶段结束后都能看到明确产出。

## 结论

柬聊接下来的开发主线应明确为：先连续推进第一阶段与第二阶段，把整体生产度提升到 `70%`；完成一次真实联调复盘后，再进入第三阶段与第四阶段，最终补到正式生产运营级 `100%`。

这份设计用于约束后续推进顺序，避免阶段 2、阶段 3 的扩功能需求提前侵入，导致阶段 1 生产化迟迟收不住。
