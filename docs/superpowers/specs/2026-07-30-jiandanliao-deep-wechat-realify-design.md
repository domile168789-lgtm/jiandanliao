# 柬单聊四个 Tab 深层微信化能力补齐设计

## 目标

- 在现有四个 Tab 微信化首页基础上，继续把高频能力从“可点入口”推进到“真实功能链路”。
- 保持 Web/H5 为本轮唯一交付端，所有实现优先复用现有 `api`、`ws`、preview store、Prisma 和 MySQL 初始化结构。
- 采用“整体范围一次性确认、实现按阶段推进并持续推仓”的方式，降低大范围改动的回归风险。

## 当前现状

- 已完成四个 Tab 首页微信式信息架构改版。
- 已完成 `消息 -> + -> 发起群聊` 真链路。
- 已完成 `新的朋友 / 标签 / 搜一搜` 的 API 化，后端已有 `friends / tags / search` 接口与 preview fallback。
- 仍未做实的高频缺口主要集中在：
  - 消息真链路：未读、已读、图片、语音、实时推送。
  - 通讯录真链路：主动添加好友、好友资料、关系管理。
  - 群管理：群成员、邀请、退群等高频管理页。
  - 我的与发现：资料编辑、黑名单/隐私、真扫码，以及若干仍偏静态的服务页。

## 设计原则

- 真实链路优先，不新增只读壳页面。
- 优先补高频闭环，再补管理能力，最后补发现与服务真实化。
- 前后端一起设计：每个 Web 页面都要有对应 API、preview 数据和测试。
- 每一阶段都要求可单独提交、测试、验收并推送到正式仓库。
- 不做无关重构，只在相关模块内补齐边界和复用。

## 范围分期

### 第一阶段：消息真链路

目标：把聊天主流程补到“接近微信高频使用”的程度。

- 会话列表补未读红点、未读数、已读状态参与展示。
- 进入会话后清理当前用户未读状态，并同步会话列表。
- 聊天页补图片发送能力：
  - Web 端支持选择图片并上传。
  - 消息列表显示图片卡片或缩略图。
- 聊天页补语音发送能力：
  - 先支持录音文件上传或浏览器录音能力。
  - 支持语音消息列表项与播放控件。
- Web 端接入真实 `ws` 消息推送与断线重连。
- preview 模式下也保持可演示的消息推送与未读更新行为。

### 第二阶段：通讯录与群管理

目标：把“找人、加人、建群后继续管理”做成闭环。

- 通讯录补主动添加好友链路：
  - 搜索手机号/昵称。
  - 查看候选用户资料。
  - 发送好友申请与附言。
  - 在“新的朋友”页处理收到的申请。
- 补好友资料页：
  - 查看昵称、手机号、标签、备注等。
  - 发消息入口。
  - 删除好友、拉黑、举报等管理项。
- 标签页扩展为成员管理：
  - 查看标签成员。
  - 为标签增减联系人。
- 群聊补管理页：
  - 查看群成员。
  - 邀请成员。
  - 退群。
  - 群主可移除成员或转让群主，若现有后端能力不足则先落管理页和已支持动作。
- 保持建群、群会话、群管理之间的路由可串联。

### 第三阶段：我的与发现真实化

目标：把“我的”和“发现”里最常用但仍偏静态的功能做成真实能力或可靠链路。

- 我的页补资料编辑：
  - 修改昵称。
  - 修改头像或头像上传入口。
- 安全/设置补高频管理项：
  - 设备登录状态。
  - 黑名单。
  - 隐私相关开关。
- 发现页补真扫码方案：
  - 优先支持上传二维码图片识别。
  - 如浏览器能力允许，再补摄像头扫码。
- 朋友圈、收藏、卡包、表情按优先级做真实化：
  - 至少把最常用的一项从本地静态升级为 API 驱动。
  - 其余保留可访问页面，但要减少演示痕迹。

## 数据与接口设计

### 消息阶段

- 扩展消息接口支持图片和语音类型的上传、发送、回显。
- 扩展会话列表返回字段，至少包含：
  - `unreadCount`
  - `isMuted`
  - `isPinned`
  - `lastReadAt` 或等价状态
- 补充消息已读接口或在现有拉取/进入会话接口中完成已读更新。
- Web 端通过 `ws` 接收新增消息、会话更新、已读状态变化。

### 通讯录与群阶段

- 新增好友申请发送接口。
- 新增好友资料查询接口。
- 新增好友关系管理接口：
  - 删除好友
  - 拉黑
  - 举报
- 扩展标签接口支持成员列表与成员变更。
- 复用已有群邀请、退群接口，并按需要补群成员列表/群设置接口。

### 我的与发现阶段

- profile 模块补编辑资料接口。
- security/settings 模块补设备、黑名单、隐私配置接口。
- scan 模块优先实现图片识别入口，识别结果按现有跳转模型复用。

## 前端设计

### 消息

- `MainShell` 会话列表新增状态位展示，但保持当前轻量微信式列表样式。
- `ChatPage` 输入区扩展为：
  - 文本输入
  - 图片上传按钮
  - 语音发送按钮
- 图片与语音消息在消息流中采用不同气泡样式，避免与文本混淆。

### 通讯录与群

- 新增“添加朋友”搜索与资料页，不把所有动作都堆在 `新的朋友` 页。
- 联系人详情页承接标签、备注、删除、拉黑、举报。
- 群管理页作为聊天页二级入口，避免主聊天页过重。

### 我的与发现

- 资料页从只读卡片升级为“查看 + 编辑”。
- 安全/设置页保留现有结构，但逐步把静态说明替换成真实设置项。
- 扫一扫保持简单路径：先图片识别，再逐步扩展摄像头。

## 测试与验收

- 每个阶段都补对应的 API 路由测试。
- 每个阶段都补对应的 Web 页面测试，至少覆盖：
  - 数据加载
  - 关键动作
  - 错误态
  - 状态刷新
- 每个阶段结束都运行：
  - `pnpm --filter @jianliao/api test -- --runInBand`
  - `pnpm --filter @jianliao/api build`
  - `pnpm --filter @jianliao/web test -- --runInBand`
  - `pnpm --filter @jianliao/web build`
- 每个阶段都更新验收文档并推送正式仓库。

## 交付方式

- 第一阶段完成后立即提交、推仓、回报提交号。
- 第二阶段在第一阶段稳定后继续提交、推仓、回报提交号。
- 第三阶段完成后再做一次整体回归，确保四个 Tab 的信息架构与真实能力一致。

## 风险与边界

- 语音消息在 Web 端受浏览器能力约束，优先保证“能发送、能播放”，不追求原生级体验。
- 真扫码若浏览器摄像头权限受限，优先交付图片识别链路。
- 朋友圈、收藏、卡包、表情不承诺本轮全部完整产品化，但至少要把其中最高频的一项做成真实 API 驱动，避免全部停留在本地静态。
- 若某些后端能力在现有仓库完全缺失，允许先补数据库模型、preview fallback 与 Web/API 统一接口，再逐步切换正式数据源。
