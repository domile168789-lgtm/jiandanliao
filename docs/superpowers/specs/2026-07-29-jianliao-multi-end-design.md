# 柬聊多端平台设计

## 背景

柬聊需要以尽快上线、尽快推广、尽快运营为目标，建设一套支持多端并行开发的即时通讯平台。产品同时覆盖：

- 安卓用户端：Kotlin 原生
- iOS 用户端：Swift 原生
- Web 管理后台
- Windows 桌面管理后台
- 共享后端平台：API、WebSocket、MySQL、Redis、文件存储、权限、审计、部署

当前目标不是先做一个功能最全的平台，而是先做一个可上线、可拉新、可运营、可继续扩展的版本，并按 `基础聊天 → 完整 IM 核心 → 运营扩展` 的顺序持续推进。

## 目标

本设计的目标如下：

- 定义多端统一的系统边界和职责分工
- 明确三阶段功能范围，避免开发范围失控
- 保证四个前端可以并行开发，但只依赖一套共享后端平台
- 以 MySQL 作为唯一主数据源，确保后续审计、运营、风控和统计口径一致
- 支撑尽快上线试运营，并为中柬旅游合作带来的推广节奏预留扩展空间

## 非目标

以下内容不属于阶段 1 的实现目标：

- 音视频通话
- 复杂轻应用容器
- 完整本地生活平台交易闭环
- 大而全的数据中台和 BI 能力
- Web 与 Windows 后台的 UI 代码复用

这些内容只有在阶段 1 稳定上线并收集到真实使用反馈后，才进入后续阶段。

## 总体方案

采用方案 A：共享后端、四端独立前端开发。

### 前端端口

#### 安卓用户端

安卓端使用 Kotlin 原生开发，承载普通用户的主要聊天和运营入口。阶段 1 重点包含：

- 注册、密码登录、短信验证码登录
- 通讯录
- 会话列表
- 单聊聊天页
- 图片消息
- 个人资料与基础设置

#### iOS 用户端

iOS 端使用 Swift 原生开发，承担与安卓端一致的业务能力，但完全按 iOS 原生交互规范独立实现，不共享 UI 层。

#### Web 管理后台

Web 后台面向运营、审核、客服、管理员，负责：

- 用户搜索与详情
- 封禁/解封
- 举报查看与处理
- 公告发布
- 操作审计
- 运营配置和基础统计看板

#### Windows 桌面管理后台

Windows 桌面后台与 Web 后台独立开发，共用后端接口，但 UI 和操作流程单独设计。它更偏值班和高频处理工作台，适合：

- 客服值班
- 高频审核
- 实时告警处理
- 快速封禁/解封
- 快速公告和风险响应

### 后端平台

共享后端平台由以下模块组成：

- `Auth`：注册、密码登录、短信登录、刷新令牌、设备管理
- `User`：用户资料、好友关系、通讯录、封禁状态
- `Conversation`：单聊、群聊、会话成员、会话摘要、未读数
- `Message`：文本、图片、文件、语音、视频消息，消息状态、撤回、回执
- `Admin`：后台用户管理、公告、举报、操作审计、风控
- `File`：文件上传、访问控制、元数据管理

### 基础设施

- `MySQL`：唯一主数据源
- `Redis`：实时事件分发、在线状态、短时缓存
- `WebSocket`：消息、回执、在线状态、后台告警实时推送
- `MinIO` 或兼容对象存储：图片、文件、语音、视频
- `Nginx`：反向代理、静态资源分发、统一入口
- `Docker Compose`：开发与服务器部署编排

## 数据模型

阶段 1 核心数据模型如下：

- `users`
- `user_credentials`
- `user_devices`
- `conversations`
- `conversation_members`
- `messages`
- `message_receipts`
- `admin_actions`
- `announcements`
- `reports`

### 关系约束

- 一个用户可以有多个设备登录记录
- 一个会话可以有多个成员
- 每条消息属于一个会话和一个发送者
- 每条消息可以有多个回执
- 后台敏感操作必须写入审计日志

### 数据原则

- 业务真实状态只看 MySQL
- Redis 中的数据不作为最终业务依据
- 文件只在存储服务保存实体，数据库只保存元数据和访问控制信息

## 核心业务链路

## 登录链路

1. 用户提交手机号 + 密码，或手机号 + 短信验证码
2. 后端校验身份
3. 签发 `accessToken` 和 `refreshToken`
4. 写入 `user_devices`
5. 客户端持久化 token，并按刷新策略续期

## 发消息链路

1. 客户端发起 `POST /api/messages`
2. 后端从 token 推导发送者身份
3. 消息写入 MySQL
4. 更新会话摘要与更新时间
5. 发布消息事件到 Redis
6. WS 服务订阅并广播到对应会话房间
7. 接收端写送达/已读回执

## 回执链路

1. 客户端收到消息后写 `DELIVERED`
2. 用户阅读消息后写 `READ`
3. 回执落 MySQL
4. Redis 广播事件
5. WS 广播给同会话相关端

## 后台封禁链路

1. 管理员查询目标用户
2. 执行封禁或解封
3. 用户状态写回 MySQL
4. 写入 `admin_actions`
5. 被封禁用户后续登录、发消息等操作被拒绝

## 接口边界

四端共用统一的接口分组：

- 用户鉴权接口
- 用户资料与通讯录接口
- 会话接口
- 消息接口
- 文件接口
- 后台管理接口
- 实时事件协议

### 实时事件协议

阶段 1 统一约定：

- `message:new`
- `receipt:new`
- `conversation:update`
- `presence:update`
- `admin:alert`

这样安卓、iOS、Web 后台、Windows 后台都能基于同一事件协议接入。

### 用户侧角色

- 普通用户
- 被封禁用户

### 后台角色

- 超级管理员
- 运营管理员
- 审核员
- 客服值班员

### 权限规则

- 所有后台操作都必须经过角色校验
- 所有后台敏感操作都必须记录审计日志
- 所有后台操作都必须能够按用户、时间、动作进行追溯

## 错误处理

必须覆盖以下失败场景：

- 登录失败：账号不存在、密码错误、验证码无效、账号被封
- 消息失败：会话不存在、无权限、文件上传失败、服务异常
- WS 失败：断线、重连、消息补拉
- 后台失败：权限不足、目标不存在、重复操作、审计失败

### 客户端行为原则

- 所有关键动作必须有清晰状态反馈
- 聊天消息支持发送中、发送成功、发送失败
- WS 断线后自动重连
- 重连后自动补拉近期消息和会话状态

## 部署方案

服务器部署采用：

- `nginx`
- `api`
- `ws`
- `mysql`
- `redis`
- `minio`

统一通过 `docker compose` 管理。

### 部署顺序

1. 启动 MySQL、Redis、MinIO
2. 启动 API、WS
3. 配置 Nginx 入口
4. 挂载前端静态资源
5. 安卓和 iOS 指向正式 API/WS 域名

## 实施顺序

尽管是四端并行开发，实施顺序必须以后端能力为中轴：

1. 先把共享后端平台做到阶段 1 可联调
2. 同步推进 Android 和 iOS 基础聊天页面
3. 同步推进 Web 后台和 Windows 值班后台最小能力
4. 后端链路稳定后尽快部署到服务器
5. 形成阶段 1 可推广版本
6. 连续推进阶段 2 和阶段 3

这保证了产品既能尽快上线，也不会因为端侧先行导致后端接口反复推倒重来。

## 风险与约束

### 主要风险

- 四端并行导致接口频繁变动
- 阶段 1 范围膨胀，拖慢上线
- 实时链路在弱网环境下表现不稳定
- 后台权限与审计模型如果设计过晚，会导致补救成本高

### 控制方式

- 先冻结阶段 1 接口契约
- 严禁把阶段 2、阶段 3 功能偷带入阶段 1
- 所有后台敏感操作先设计权限和审计，再做页面
- WS 永远只做实时分发，最终状态一律回到 MySQL 校准

## 结论

柬聊多端平台采用共享后端、四端独立开发的方案，按 `基础聊天 → 完整 IM 核心 → 运营扩展` 顺序推进。阶段 1 以最小可推广、可运营、可上线为目标，确保能尽快支撑推广和试运营；阶段 2、阶段 3 在此基础上持续扩展。

该设计是后续实现计划和全面开发的唯一基准文档。任何超出阶段 1 的能力，都必须明确归入后续阶段，而不是在执行过程中无约束扩张。
