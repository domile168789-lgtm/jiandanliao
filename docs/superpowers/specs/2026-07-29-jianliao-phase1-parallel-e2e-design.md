# 柬聊阶段 1 并行联调与部署设计

## 背景

柬聊的阶段 1 共享后端、Android 用户端、iOS 用户端、Web 管理后台、Windows 桌面管理后台已经有了第一版骨架，但当前还缺少一份明确的并行推进设计，把“先做什么、并行做到什么程度、如何验收”统一下来。

当前最重要的目标不是继续铺更多功能，而是尽快把一条可演示、可复现、可迁移到服务器的端到端闭环跑通。为此，需要在不打乱既有后端契约的前提下，定义并行子项目边界、固定关键数据流，并给出统一验收标准。

## 目标

- 以方案 A 固定阶段 1 的推进方式：本地闭环为主线，服务器部署为影子线
- 让 Android、iOS、Web 后台、Windows 后台能够并行推进，但只消费一套共享后端契约
- 固定用户端聊天链路、后台操作链路、部署链路，避免各端各自演化
- 明确这一轮的关键失败点与边界，避免把阶段 2、阶段 3 的内容混入阶段 1
- 为后续实施计划与子代理拆分提供单一依据

## 非目标

这一轮设计不包含以下内容：

- 恢复短信验证码登录
- 群聊、语音、视频、文件消息等阶段 2 能力
- 高级后台能力，如搜索、筛选、批量操作、看板增强
- 生产级签名上传、对象存储权限收紧、完整安全加固
- 复杂 UI 美化与跨端统一设计系统

## 推荐方案

采用方案 A：`本地联调闭环主线 + 服务器部署影子线并行`。

### 选择理由

- 本地闭环能最快拿到可演示 MVP，接口、上传、WS、回执等问题更容易定位
- 服务器影子线同步推进，可以尽早暴露域名、反代、上传路径、环境变量等真实部署问题
- 与“全部直接围绕服务器联调”相比，方案 A 更稳定，排障成本更低
- 与“只做部署再接客户端”相比，方案 A 更符合当前“尽快跑通端到端”的目标

## 并行架构

### 主线

主线目标是先形成一个本地可演示的端到端闭环。主线包含 3 个并行子项目：

- 子项目 A：本地闭环编排
- 子项目 B：Android / iOS 用户端联调闭环
- 子项目 C：Web / Windows 管理后台联调闭环

这 3 条线全部依赖 `docs/api-contracts/phase1-backend.md` 作为共享后端契约。端侧不允许绕过契约自行定义新接口；一旦发现契约缺口，必须回到共享后端统一补齐。

### 影子线

影子线是子项目 D：服务器部署与反代收口。它与主线并行推进，但不反向阻塞主线。影子线的职责是保证本地闭环迁移到服务器时，不需要修改客户端的业务逻辑和核心时序。

## 子项目边界

### 子项目 A：本地闭环编排

子项目 A 只负责建立统一的本地联调基线，不负责业务页面和体验打磨。它的交付物包括：

- 本地一键启动说明或脚本
- 初始化阶段 1 数据的脚本与顺序
- 本地联调检查清单
- 各端统一的本地访问地址约定
- 上传入口与 Socket.IO 入口的统一约定

子项目 A 是所有端的公共底座，优先级最高。

### 子项目 B：用户端联调闭环

子项目 B 只关心普通用户是否能完成完整聊天路径，范围锁定为：

- 注册
- 密码登录
- refresh token
- 会话列表
- 单聊消息列表
- 发文本消息
- 发图片消息
- 收消息、收回执、断线重连

本子项目暂不扩短信登录、群聊、复杂 UI、搜索与发现页。

### 子项目 C：后台管理联调闭环

子项目 C 只关心后台的最小运营闭环，范围锁定为：

- 管理员身份录入与保存
- 用户列表
- 封禁用户
- 举报列表
- 发布公告
- 审计列表

Web 和 Windows 桌面是两个独立前端，但共用同一套后台接口语义与最小操作流，不允许功能分叉。

### 子项目 D：服务器影子线

子项目 D 只负责把主线结果迁移到真实服务器时的最小返工压到最低。范围锁定为：

- `docker compose` 环境变量模板
- `nginx` 反代路径与健康检查
- `uploads` 对外路径设计
- 初始化数据与启动步骤
- 服务器联调说明与验证顺序

本子项目暂不扩更重的生产级安全增强与运维监控能力。

## 依赖关系

依赖关系固定如下：

1. 子项目 A 先固定本地编排基线
2. 子项目 B 与子项目 C 在 A 的基线之上并行推进
3. 子项目 D 同步跟进，但只消费 A/B/C 已确认的路径，不反向修改主线结构

这个顺序的原则是：服务器线不能拖住客户端线，部署问题不能反向要求用户端改业务路径。

## 核心数据流

### 用户端数据流

Android 和 iOS 必须共用完全一致的业务时序：

1. `POST /api/auth/register` 或 `POST /api/auth/login/password`
2. `POST /api/auth/refresh-token` 维持会话
3. `GET /api/conversations`
4. 进入单聊后 `GET /api/messages`
5. 发文本消息走 `POST /api/messages`
6. 发图片消息时先走 `POST /api/files/upload`
7. 客户端 `PUT uploadUrl`
8. 再发 `type=IMAGE` 的 `POST /api/messages`
9. 通过 `Socket.IO` 接收 `message:new` / `receipt:new`

不允许出现一端先传图再拿元数据、另一端先拿元数据再传图的分叉时序。

### 后台数据流

后台最小操作流固定为：

1. 登录后写入 `x-admin-role` 与 `x-admin-id`
2. 进入用户页，读取 `GET /api/admin/users`
3. 封禁用户，调用 `POST /api/admin/users/:id/ban`
4. 进入举报、公告、审计页面，分别调用各自后台接口

Web 与 Windows 桌面后台必须共享同一套后台操作语义；差异只允许存在于壳层和交互方式，不允许存在于业务能力定义上。

### 部署数据流

部署主路径固定为：

1. `docker compose up -d --build`
2. 验证 `nginx`、`api`、`ws`、`mysql`、`redis`、`minio` 健康检查
3. 执行初始化数据脚本
4. 所有客户端只通过统一入口访问：
   - `/api`
   - `/socket.io/`
   - `/uploads/`

客户端不得直接依赖容器内部地址，例如 `minio:9000`。对客户端可见的上传入口必须统一收口到 `nginx + /uploads/`。

## 关键失败点

### 上传地址不一致

如果后端返回的 `uploadUrl` 在本地或服务器环境不可达，图片消息链路就会断。阶段 1 必须统一使用对客户端可达的上传入口，不能让移动端和后台直接依赖容器内域名。

### WS 连接语义不一致

如果 Android、iOS、Web、Windows 对 `auth:authenticate` 和 `conversation:join` 的时机处理不同，就会出现 HTTP 发消息成功但实时收不到的伪故障。阶段 1 必须把 WS 连接顺序固定下来。

### 演示数据不可复现

如果每次联调依赖不同数据库状态，就无法稳定复测。初始化脚本必须成为主线的一部分，而不是可选辅助脚本。

### 后台身份注入方式不统一

阶段 1 后台用 header 标识管理员身份，这种方式简单但容易因端侧实现分叉而导致行为不一致。Web 和 Windows 必须统一管理员身份的保存、注入和退出规则。

## 验收标准

### 子项目 A 验收

- 一条命令能启动本地后端基础服务
- 一条命令能初始化阶段 1 演示数据
- 文档中明确所有端的本地 base URL
- 文档中明确检查顺序：健康检查、登录、消息、上传、后台

### 子项目 B 验收

- 两个账号可以注册并登录
- 可以创建单聊
- 可以互发文本消息
- 可以发送图片消息
- 可以收到 `READ` 回执
- 断线后可以重新连接并继续收消息

### 子项目 C 验收

- Web 后台可以查用户、封禁、看举报、发公告、看审计
- Windows 后台可以完成相同的最小操作流
- 两端接口行为一致，不出现功能分叉

### 子项目 D 验收

- 有明确的环境变量模板
- 有明确的部署步骤
- 有统一对外访问路径
- 有初始化与验证步骤
- 本地闭环迁移到服务器时不需要改客户端业务逻辑

## 实施拆分建议

后续正式实施应拆为 4 组任务：

- 任务 1：本地闭环编排与联调文档
- 任务 2：Android / iOS 用户端联调闭环
- 任务 3：Web / Windows 后台联调闭环
- 任务 4：服务器部署影子线收口

每组任务只对自己的边界负责，最后统一由主控会合并验收。

## 风险控制原则

- 阶段 1 只允许修契约缺口，不允许扩范围
- 服务器影子线只消费已定路径，不反向改动主线业务设计
- 用户端与后台端都必须先保证链路完整，再考虑 UI 细化
- 任何实时状态最终都回到 MySQL 和接口补拉校准，不能仅依赖 WS 内存状态

## 结论

阶段 1 的下一步应按方案 A 推进：本地闭环作为主线，服务器部署作为影子线，并拆成 4 个并行子项目执行。这样可以在最短时间内拿到可演示的端到端 MVP，同时避免从本地迁移到服务器时产生大规模返工。

这份设计是后续实施计划和子代理拆分的直接依据。超出本设计范围的内容，统一延后到下一轮需求确认，而不是在执行过程中扩张。
