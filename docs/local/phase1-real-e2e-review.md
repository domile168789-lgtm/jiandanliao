# 阶段 1 达到 70% 时的真实联调复盘清单

## 目标

本清单用于判断阶段 1 是否已经从“本地可跑”推进到“可做一次真实联调复盘”的 70% 状态。复盘时必须同时覆盖服务器、移动端、后台与日志定位链路。

## 复盘对象

- 服务器部署是否稳定
- 管理后台最小操作流是否连续可用
- iOS / Android 是否能真实互发文本和图片
- 上传与回执链路是否稳定
- 日志与问题记录是否足够支撑定位

## 复盘前置条件

1. 本地主线服务已启动，并完成一次健康检查。
2. 演示数据或联调账号已经初始化完成。
3. iOS、Android 与管理后台都已确认各自入口地址。
4. 复盘参与者明确记录时间、环境、账号、设备信息。

## 复盘清单

### 1. 服务器部署是否稳定

- [ ] API、WS、Uploads 入口在联调期间持续可访问
- [ ] 健康检查通过后再开始移动端与后台联调
- [ ] 服务异常时能从 compose / 服务日志快速定位到对应组件
- [ ] 出现失败后，有明确的恢复步骤与重试结果记录

### 2. 管理后台

- [ ] 管理后台使用统一管理员身份与同一 API Base URL
- [ ] 能完成 `GET /api/admin/users`
- [ ] 能完成 `POST /api/admin/users/:id/ban`
- [ ] 能完成 `GET /api/admin/reports`
- [ ] 能完成 `POST /api/admin/announcements`
- [ ] 能完成 `GET /api/admin/audit-actions`
- [ ] 管理结果与服务端数据保持一致
- [ ] Windows 管理后台首页保持暗色仪表盘布局，且“品牌配置”页可分别编辑 mobile / pc 的项目名称、LOGO、底部背景主题位
- [ ] 修改 mobile 品牌配置后，`/h5` 登录页能同步展示对应品牌变化
- [ ] 修改 pc 品牌配置后，`/` 登录页能同步展示对应品牌变化

> 当前仓库没有独立“用户 Windows 桌面端”代码目录。
> 本轮先将 `pc` 品牌配置作用于 `PC 网页端`，后续 Windows 用户端需接入：
> `GET /api/public/branding?group=pc`

### 3. iOS / Android

- [ ] iOS / Android 都能稳定登录
- [ ] iOS / Android 能进入同一单聊并双向发送文本消息
- [ ] iOS / Android 能进入同一单聊并双向发送图片消息
- [ ] iOS / Android 对文本与图片都能成功写入 `READ` 回执
- [ ] 任一端失败时，另一端、后台和日志都能提供定位线索

### 4. 上传与回执链路

- [ ] `/api/files/upload` 能正常返回上传元数据
- [ ] 客户端上传后，图片消息能被另一端成功拉取或实时接收
- [ ] `POST /api/messages` 对图片消息没有出现缺字段或对象键异常
- [ ] `POST /api/messages/:id/receipt` 能稳定写入回执
- [ ] 遇到重复回执、上传失败、消息未达时，有明确记录与临时规避说明

### 5. 日志与复盘输出

- [ ] 每个失败点都记录了时间、设备、账号、接口、日志线索
- [ ] 每个失败点都记录了是否可复现、复现次数与恢复方式
- [ ] 已区分“服务器问题 / 移动端问题 / 后台问题 / 环境问题”
- [ ] 复盘结论已回填到对应 README 或联调清单

## 结论

- 若以上 5 个维度都能形成可复查证据，可视为阶段 1 已具备 70% 的真实联调复盘基础。
- 若任一维度仍缺少证据，先补记录与修复，再重新执行一次完整联调。
